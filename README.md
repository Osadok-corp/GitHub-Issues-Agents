# Поиск кода по GitHub issue: ChromaDB + LangChain + DeepSeek (MVP)

Агент получает GitHub issue в формате JSON (теги, краткое содержание, класс проблемы),
ищет в векторной базе ChromaDB функцию, в которой находится проблема, и отвечает:
**файл, функция, строки, одно предложение с объяснением.**

Это RAG (Retrieval-Augmented Generation): сначала *поиск* релевантного кода в базе,
затем *генерация* ответа языковой моделью по найденному коду.

Документ рассчитан на контрибьюторов: после него должно быть понятно, **что лежит
в ChromaDB, как файлы режутся на куски, как работает поиск и что менять, если
качество поиска надо улучшить.**

## Быстрый старт

```bash
pip install -r requirements.txt
```

**Ключ DeepSeek.** Получите его на [platform.deepseek.com](https://platform.deepseek.com)
(API платный, обычно нужен положительный баланс; цены смотрите на сайте DeepSeek).
Код читает ключ из переменной окружения `DEEPSEEK_API_KEY`:

| Где запускаете | Команда |
|---|---|
| Linux / macOS | `export DEEPSEEK_API_KEY=sk-...` |
| Windows PowerShell | `$env:DEEPSEEK_API_KEY="sk-..."` (только для этого окна) |
| Windows, навсегда | `setx DEEPSEEK_API_KEY "sk-..."`, затем **перезапустить терминал / PyCharm** |
| PyCharm | Run → Edit Configurations → Environment variables |

> **Никогда не вписывайте ключ в код и не коммитьте его.** Если `ChatDeepSeek(...)` в
> `agent_demo.py` вызывается с аргументом `api_key="..."`, уберите его: без этого аргумента
> ключ берётся из переменной окружения.

**Запуск:**

```bash
# 1. Построить индекс (создаст папку chroma_db/)
python vector_db.py index https://github.com/owner/repo

# 2. Проверить поиск БЕЗ языковой модели
python vector_db.py search "discount percent is calculated wrong"

# 3. Полный сценарий: issue -> агент -> ответ
python agent_demo.py sample_issue.json
```

Для проверки без сети есть локальный репозиторий: `python vector_db.py index demo_repo`.
`sample_issue.json` описывает баг именно из него (`Cart.apply_discount` вычитает процент
как число). Ожидаемый ответ агента: `shop/cart.py`, `Cart.apply_discount`, строки 17–19.
Для другого репозитория нужен свой issue-JSON.

При первом поиске или индексации Chroma скачивает модель эмбеддингов (~80 МБ) в
`~/.cache/chroma/` (на Windows: `C:\Users\<имя>\.cache\chroma\`). Это происходит один раз.

Необязательно: `GITHUB_TOKEN` поднимает лимит GitHub API с 60 до 5000 запросов в час.

## Структура проекта

```
github_parsing.py   # парсинг GitHub: issue, дерево файлов репозитория, скачивание файла
vector_db.py        # всё про ChromaDB: загрузка, чанкинг, индексация, поиск (CLI тоже здесь)
agent_demo.py       # LangChain-агент на DeepSeek с инструментом search_code
sample_issue.json   # пример issue (теги, краткое содержание, класс проблемы)
demo_repo/          # маленький локальный репозиторий с известным багом, для проверки
requirements.txt
chroma_db/          # создаётся при индексации; в git не коммитить
```

## Общая схема

```
          ┌──────────────── ИНДЕКСАЦИЯ (один раз на репозиторий) ────────────────┐
          │                                                                      │
GitHub ──►│ get_repo_raw_urls ─► download .py ─► chunk_python_source ─► Chroma   │
 repo     │   (список файлов)    (текст файлов)   (1 функция = 1 чанк)  .add()   │
          └──────────────────────────────────────────────────────────────────────┘

          ┌──────────────────────────── РАБОТА АГЕНТА ───────────────────────────┐
issue.json│                                                                      │
   │      │   DeepSeek ──► tool search_code("текст запроса") ──► Chroma.query()  │
   └─────►│      ▲                                                    │          │
          │      └───────── топ-3 функции (код + путь + строки) ◄─────┘          │
          │      │  (может искать несколько раз с разными запросами)             │
          │      ▼                                                               │
          │   ответ: файл, функция, строки, объяснение                           │
          └──────────────────────────────────────────────────────────────────────┘
```

Языковая модель **не видит весь репозиторий**. Она видит только issue и те несколько
функций, которые вернул поиск. Поэтому качество ответа почти целиком определяется
качеством поиска: если нужной функции нет в выдаче, модель её не найдёт.

## ChromaDB: что это и что мы в ней храним

ChromaDB — векторная база данных. Обычная БД ищет по точному совпадению («найди строки,
где `name = 'cart'`»). Векторная ищет **по смыслу**: каждый текст превращается в
набор чисел (вектор, *эмбеддинг*), и тексты с похожим смыслом получают близкие векторы.
Запрос «скидка считается неправильно» окажется рядом с функцией `apply_discount`, даже
если слова в них не совпадают.

### Ключевые понятия

| Понятие | Что это | У нас |
|---|---|---|
| **Client** | Подключение к базе | `chromadb.PersistentClient(path="chroma_db")`: данные лежат на диске |
| **Collection** | Аналог таблицы: набор записей одного типа | одна коллекция `code_chunks` |
| **Document** | Текст записи | текст чанка: заголовок + код функции |
| **Embedding** | Вектор документа | считает Chroma сама, мы его не трогаем |
| **Metadata** | Словарь произвольных полей | `file`, `name`, `start_line`, `end_line` |
| **id** | Уникальный ключ записи | `shop/cart.py:Cart.apply_discount:17` |

Одна запись в коллекции целиком:

```
id         : shop/cart.py:Cart.apply_discount:17
document   : # file: shop/cart.py
             # function: Cart.apply_discount
                 def apply_discount(self, total, percent):
                     """Apply a percentage discount ... to the total price."""
                     return total - percent
embedding  : [0.021, -0.113, ...]   (384 числа, считается автоматически)
metadata   : {"file": "shop/cart.py", "name": "Cart.apply_discount",
              "start_line": 17, "end_line": 19}
```

### Как Chroma превращает текст в вектор

Мы используем `DefaultEmbeddingFunction`. Это модель **all-MiniLM-L6-v2**
(формат ONNX): она работает локально на CPU, не требует ключей и PyTorch. Что важно знать:

- Вектор имеет 384 числа.
- **Модель читает не более 256 токенов текста.** Всё, что длиннее, отбрасывается *при
  подсчёте вектора*. Сам документ при этом хранится целиком, и агенту вернётся полный
  код. Значит, у длинной функции смысл вектора определяют её первые строки, а
  заголовок (`# file`, `# function`) тоже входит в эти 256 токенов.
- Модель общего назначения, не «кодовая»: хорошо понимает английские имена и комментарии,
  хуже глубоко разбирается в логике кода.
- Запрос превращается в вектор **той же** функцией, поэтому запросы и документы сравнимы.

### Как Chroma ищет

Для каждого запроса Chroma находит векторы, ближайшие к вектору запроса. Чтобы не
сравнивать со всеми записями по очереди, она строит индекс **HNSW** (приближённый
поиск ближайших соседей, быстрый даже на сотнях тысяч записей).

**Метрика расстояния — косинусная** (`{"hnsw": {"space": "cosine"}}`). Это *расстояние*:

- **меньше = ближе**; значение 0 означает полное совпадение направления векторов;
- диапазон от 0 до 2, на практике похожие тексты дают значения примерно до 0.5–0.6;
- абсолютные значения зависят от модели и репозитория, **не используйте жёсткий порог**
  (типа «берём только distance < 0.4»); сравнивайте результаты между собой.

Косинусную метрику выбрали, потому что для текстовых эмбеддингов важно *направление*
вектора, а не его длина. Метрика по умолчанию у Chroma (L2) этого не гарантирует.

### Что лежит в `chroma_db/`

- `chroma.sqlite3` хранит документы, метаданные и id;
- папка с UUID в имени хранит HNSW-индекс с векторами.

Папку можно удалить: индекс просто построится заново командой `index`.

## Шаг 1. Загрузка кода с GitHub

Код: `github_parsing.py` и функции `load_files_from_github` / `load_files_from_folder`
в `vector_db.py`.

1. `get_repo_raw_urls(repo_url, token)` обращается к GitHub API: узнаёт основную ветку
   репозитория, получает рекурсивное дерево файлов и возвращает словарь
   `{путь_в_репозитории: raw-ссылка}`. Это **2 запроса к API** независимо от размера
   репозитория.
2. `is_wanted(path)` оставляет только файлы, которые стоит индексировать: `.py` и не
   лежащие в папках из `SKIP_DIRS` (`tests`, `test`, `docs`, `doc`, `examples`,
   `benchmarks`). Баг ищем в рабочем коде, а тесты только засоряют выдачу
   (в тесте `test_discount` будет всё те же слова, что и в баге).
3. `download(url)` скачивает каждый файл (`parse_code_by_url`) по raw-ссылке. Скачивание
   идёт в 8 потоков, потому что на большом репозитории это сотни сетевых запросов.
   Файл, который не скачался, пропускается и не прерывает индексацию.

Итог шага: словарь `{путь: текст файла}`. Дальше работа идёт только с текстом, поэтому
источник (GitHub или локальная папка) на остальной код не влияет.

> Индексируется **основная ветка на момент запуска**. Если issue относится к старой
> версии, номера строк в ответе могут не совпасть.

## Шаг 2. Разбиение файлов на чанки

Код: `chunk_python_source(source, rel_path)` в `vector_db.py`.

### Зачем нужны чанки

Один вектор описывает один текст. Если положить в базу файл целиком, вектор будет
«про всё сразу» и размоется; если резать по N символов, функции разорвутся
посередине. А нам нужен **ответ уровня «файл + функция + строки»**. Поэтому:

> **один чанк = одна функция или один метод класса.**

| Вариант | Проблема |
|---|---|
| Файл целиком | Вектор усредняет смысл десятка функций; issue про одну функцию его не «перетянет» |
| Окна по N строк | Функция рвётся пополам, в вектор попадает смесь двух несвязанных кусков |
| **Функция (наш выбор)** | Естественная смысловая единица, именно её мы хотим вернуть |

### Как режем

Используется стандартный модуль `ast`: он разбирает текст как настоящий Python-код
(а не регулярками), поэтому корректно находит границы функций, декораторы, вложенные
скобки и многострочные строки.

1. `ast.parse(source)` строит дерево. Если файл не разбирается (Python 2, шаблоны
   с синтаксисом вроде `{{ }}`), он **целиком пропускается**.
2. Из верхнего уровня файла берутся:
   - функции (`def`, `async def`);
   - методы классов: для каждого класса берутся его `def` / `async def`.
3. Для каждой функции вырезаются строки от первого декоратора (если он есть) до
   `end_lineno`. Докстринг и комментарии внутри функции попадают в чанк, потому что это
   самое «смысловое» в функции.
4. К коду спереди добавляются две строки заголовка:

   ```
   # file: shop/cart.py
   # function: Cart.apply_discount
   ```

   **Зачем заголовок:** он тоже попадает в эмбеддинг. Благодаря ему issue со словом «cart»
   притягивается к файлу `cart.py`, даже если в теле функции этого слова нет, а имя
   `Cart.apply_discount` само по себе несёт смысл. Это дёшево и заметно помогает.
5. Формируется `id` = `путь:имя:первая_строка` (уникален в пределах репозитория) и
   метаданные `file`, `name`, `start_line`, `end_line`. Номера строк нужны, чтобы в
   ответе агента были точные строки и не приходилось заново разбирать код.

### Что НЕ попадает в индекс (известные пробелы)

- Код уровня модуля (константы, конфиги, скрипты без функций).
- Атрибуты и тело класса вне методов.
- Функции, определённые внутри `if`, `try`, `with` на верхнем уровне
  (например, под `if TYPE_CHECKING:`); и методы вложенных классов.
- Вложенные функции отдельным чанком не идут, они остаются внутри текста родителя.
- Все файлы не на Python.
- Очень длинные функции: в эмбеддинге учитываются только первые 256 токенов.

Если баг лежит в одной из таких «слепых зон», агент его не найдёт. Это первое место,
которое стоит проверить, если нужная функция не находится.

## Шаг 3. Индексация

Код: `build_index(repo)` в `vector_db.py`.

```
files  = load_files_from_github(url)  или  load_files_from_folder(path)
chunks = chunk_python_source(...) для каждого файла
collection = get_collection(reset=True)      # удалить старую коллекцию и создать новую
collection.add(ids, documents, metadatas)    # порциями по 500
```

Что стоит знать:

- Мы передаём Chroma только `documents`; **эмбеддинги она считает сама** с помощью
  функции, указанной в `get_collection()`. Это самая затратная часть: на CPU считаются
  векторы для каждого чанка. Для первой проверки берите небольшой репозиторий.
- `reset=True`: каждый запуск `index` строит всё **с нуля** и заменяет предыдущий индекс.
  Так проще всего избежать устаревших и дублирующихся записей. В базе одновременно
  лежит **один** репозиторий.
- Порции по `BATCH_SIZE = 500`: у Chroma есть лимит на размер одного `add` (в нашей
  версии 5461 запись), а в большом репозитории чанков десятки тысяч.
- Если `index` не запускали, поиск вернёт пустой результат: коллекция существует, но
  пуста.

## Шаг 4. Поиск

Код: `search(query, n_results=3)` в `vector_db.py`.

```python
collection.query(query_texts=[query], n_results=3)
```

Что происходит внутри:

1. Chroma превращает строку `query` в вектор той же моделью, что и документы.
2. По HNSW-индексу находит `n_results` ближайших векторов по косинусному расстоянию.
3. Возвращает для каждого: текст, метаданные и расстояние. Ответ Chroma устроен как
   «списки списков» (по одному списку на каждый запрос; мы всегда шлём один запрос),
   поэтому в коде везде `[0]`.
4. `search()` упаковывает это в простой список словарей, отсортированный от лучшего
   к худшему: `file`, `name`, `start_line`, `end_line`, `distance`, `code`.

### Как поиск связан с агентом

Агент не передаёт в поиск сам JSON. **Модель сама формулирует текстовый запрос**
по issue (например, «apply discount percentage calculation»), вызывает инструмент
`search_code`, читает результаты и при необходимости ищет ещё раз другими словами.
Поэтому в системном промпте прямо написано, что инструмент можно вызывать несколько раз.

Инструмент склеивает результаты в текст такого вида (его читает модель):

```
shop/cart.py:17-19 (Cart.apply_discount)
# file: shop/cart.py
# function: Cart.apply_discount
    def apply_discount(self, total, percent):
    ...
---
shop/cart.py:21-23 (Cart.total)
...
```

> Агент получает код выдачи **целиком**, без обрезки. Три очень длинные функции могут
> занять много контекста модели.

### Как проверить поиск отдельно от LLM

```bash
python vector_db.py search "краткое содержание issue"
```

Пример вывода (числа условные):

```
shop/cart.py:17-19  Cart.apply_discount  (distance=0.41)
shop/cart.py:21-23  Cart.total  (distance=0.47)
shop/cart.py:11-13  Cart.subtotal  (distance=0.58)
```

**Рецепт оценки качества.** Возьмите 5–10 реальных issue, для которых вы знаете
правильную функцию, и для каждого посмотрите, попала ли она в топ-3 (топ-5, топ-10).
Если не попадает, проблема в чанкинге или эмбеддингах, а не в языковой модели, и
менять промпт бессмысленно.

## Агент на DeepSeek

Код: `agent_demo.py`.

- **Модель:** `ChatDeepSeek` из пакета `langchain-deepseek`, по умолчанию
  `deepseek-chat` (меняется переменной `DEEPSEEK_MODEL`). Для агента нужна модель с
  поддержкой вызова инструментов: по документации LangChain, её поддерживает
  `deepseek-chat`, а `deepseek-reasoner` нет. Список моделей DeepSeek меняется, актуальные
  названия смотрите в документации DeepSeek.
- **Инструмент `search_code(query)`:** тонкая обёртка над `search()`. Её docstring важен:
  по нему модель понимает, когда и зачем вызывать инструмент.
- **`create_agent`** запускает цикл: модель решает вызвать инструмент → получает код →
  при необходимости ищет ещё → отвечает. `temperature=0.1`, чтобы ответы были стабильными.
- **Системный промпт** требует ответ в формате: файл, функция, диапазон строк, одно
  предложение с объяснением.
- **Замена модели** занимает одну строку: вместо `ChatDeepSeek(...)` подставьте любой
  чат-класс LangChain с поддержкой инструментов (`ChatOpenAI`, `ChatAnthropic`, ...).
  `vector_db.py` при этом не меняется.

## Как вносить изменения

| Что хотите изменить | Где | Переиндексировать? |
|---|---|---|
| Сколько функций возвращает поиск | `n_results` в `search_code` (`agent_demo.py`) | нет |
| Модель DeepSeek / системный промпт | `agent_demo.py` | нет |
| Какие файлы индексировать | `is_wanted`, `SKIP_DIRS` | **да** |
| Правила разбиения на чанки, заголовок чанка | `chunk_python_source` | **да** |
| Модель эмбеддингов | `embedding_function` в `get_collection` | **да** |
| Метрика расстояния | `configuration` в `get_collection` | **да** |
| Поддержка другого языка (JS, Java, ...) | `is_wanted` + новый чанкер (например, на `tree-sitter`) | **да** |

**Почему «да, переиндексировать».** Всё, что влияет на то, *что* лежит в базе или *как*
считаются векторы, влияет на уже сохранённые записи. Векторы разных моделей
несовместимы между собой. В моей проверке Chroma не выдала ошибку, когда коллекция,
созданная одной функцией эмбеддингов, была открыта другой, так что после смены модели
результаты поиска просто станут бессмысленными. Всегда запускайте `index` заново.

**Что обычно улучшает поиск, в порядке возрастания трудозатрат:**

1. Увеличить `n_results` до 5–10 (дёшево, но больше контекста у модели).
2. Заменить эмбеддинги на «кодовые», например через `SentenceTransformerEmbeddingFunction`
   с моделью `jinaai/jina-embeddings-v2-base-code`. У многих из них окно длиннее 256 токенов.
3. Резать длинные функции на части (с тем же заголовком в каждой).
4. Гибридный поиск: к векторному добавить поиск по точным именам из issue
   (названия функций, текст исключений, стек-трейс).
5. Реранкинг: взять топ-20 из Chroma и переупорядочить отдельной моделью.

**Не коммитьте:** `chroma_db/`, `.venv/`, ключи (добавьте их в `.gitignore`).

## Частые проблемы

| Симптом | Причина и решение |
|---|---|
| `ModuleNotFoundError: langchain_deepseek` | `pip install -U langchain-deepseek` (или `pip install -r requirements.txt`) |
| Ошибка аутентификации / 401 от DeepSeek | Ключ неверный или не виден процессу. После `setx` нужно **перезапустить терминал и PyCharm** |
| Ошибка про недостаток баланса | Пополните баланс на платформе DeepSeek |
| Агент не вызывает поиск / отвечает «из головы» | Модель не поддерживает вызов инструментов (например, `deepseek-reasoner`); используйте `deepseek-chat` |
| `403` / rate limit от GitHub при индексации | Без токена лимит 60 запросов в час. Задайте `GITHUB_TOKEN` |
| Первый запуск долго «висит» | Chroma скачивает модель эмбеддингов (~80 МБ). Нужен доступ к интернету, один раз |
| Поиск возвращает пустой результат | Не запускали `index` или индексация нашла 0 `.py` файлов вне `SKIP_DIRS` |
| Индексация очень долгая | Репозиторий большой, эмбеддинги считаются на CPU. Начните с небольшого репозитория |
| В топе не та функция | См. «Рецепт оценки качества» и список «что не попадает в индекс» |

## Ограничения MVP и идеи

- Только Python и только функции/методы (см. «слепые зоны» в шаге 2).
- Один репозиторий в базе за раз; полная пересборка при каждой индексации.
- Индексируется основная ветка, а не коммит, к которому относится issue.
- Эмбеддинги общего назначения и окно в 256 токенов.
- Нет гибридного поиска и реранкинга.
- Агент получает код выдачи без обрезки.
